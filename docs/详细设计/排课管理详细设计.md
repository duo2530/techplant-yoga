| 2 | 已上架 | ✅ | ❌ | ❌ |

## 1.3 数据库物理模型

### 1.3.1 建表语句

```sql
CREATE TABLE `t_schedule` (
  `id`             bigint unsigned NOT NULL COMMENT '排课ID',
  `store_id`       bigint unsigned NOT NULL COMMENT '门店ID',
  `course_id`      bigint unsigned NOT NULL COMMENT '课程ID',
  `course_type`    tinyint      NOT NULL COMMENT '课种快照：1团课 2精品课 3私教课 4特色课',
  `coach_id`       bigint unsigned NOT NULL COMMENT '教练ID',
  `classroom_id`   bigint unsigned NOT NULL COMMENT '教室ID',
  `schedule_date`  date NOT NULL COMMENT '上课日期',
  `start_time`     datetime NOT NULL COMMENT '开始时间',
  `end_time`       datetime NOT NULL COMMENT '结束时间',
  `max_persons`    int NOT NULL COMMENT '最大人数',
  `min_persons`    int NOT NULL DEFAULT 2 COMMENT '最低开课人数',
  `booked_persons` int NOT NULL DEFAULT 0 COMMENT '已预约人数',
  `status`         tinyint NOT NULL DEFAULT 1 COMMENT '状态：1待上架 2已上架 3已取消 4已结束',
  `create_by`      bigint unsigned DEFAULT NULL COMMENT '创建人ID',
  `create_time`    datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `update_by`      bigint unsigned DEFAULT NULL COMMENT '更新人ID',
  `update_time`    datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='排课信息表';
```

## 2.3 数据模型

### 2.3.1 `ScheduleListItemVO` / `ScheduleDetailVO`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 排课ID |
| `storeId` / `storeName` | string | 门店 |
| `courseId` / `courseName` | string | 课程 |
| `courseType` | integer | **课种快照**（排课自有字段，不回读课程） |
| `courseTypeName` | string | **课种名称**（按 `CourseTypeEnum` 翻译快照码；用户端卡片与详情页直接显示它） |
| `coachId` / `coachName` | string | 教练 |
| `classroomId` / `classroomName` | string | 教室 |
| `startTime` / `endTime` | string | `yyyy-MM-dd HH:mm:ss` |
| `scheduleDate` | string | **上课日期** `yyyy-MM-dd`（筛选与日期条都用它） |
| `maxPersons` / `minPersons` | integer | 最大人数／最低开课人数 |
| `bookedPersons` | integer | 已预约人数（一期恒 0） |
| `status` | integer | 落库状态码 `1`/`2`/`3`/`4` |
| `statusText` | string | 展示文案：待上架／已上架／已取消／已结束 |
| `finished` | boolean | 是否已结束（`status = 4`，或任务尚未处理但 `end_time < now`；时间仅作为即时展示兜底） |

两个 VO 字段相同（列表已经带了排课全部业务字段，不再裁剪）。

### 2.3.2 `ScheduleCreateDTO` / `ScheduleUpdateDTO`

两个请求模型字段相同：`storeId`、`courseId`、`coachId`、`classroomId`、`startTime`、`endTime`、`maxPersons`、`minPersons`。**不含** `status`、`bookedPersons`、**`courseType`** 与 **`scheduleDate`**（课种快照由服务端从课程取、上课日期由服务端从开始时间推导）。使用 `@Valid` 校验非空；业务范围校验在 service。

### 2.3.3 `ScheduleQuery`

列表筛选与分页：`storeId`、`courseId`、`courseType`、`coachId`、`startDate`、`endDate`、`status`、`pageNum`、`pageSize`（上限 100）。

### 2.3.4 状态接口的入参

只有一个字段，直接用查询参数 `status`，**不建 DTO**。

# 3、开发架构

## 3.1 包结构

```text
com.techplant.yoga.schedule
├─ controller/ScheduleController.java          （管理端）
├─ controller/SchedulePublicController.java    （用户端，契约见《用户端接口详细设计》）
├─ service/ScheduleService.java                （同时供四个主数据模块做删除门禁统计、供用户端查询）
├─ service/impl/ScheduleServiceImpl.java
├─ dao/ScheduleDao.java、ScheduleDaoImpl.java
├─ mapper/ScheduleMapper.java
├─ domain/ScheduleDO.java
├─ dto/ScheduleCreateDTO.java、ScheduleUpdateDTO.java
├─ query/ScheduleQuery.java
├─ vo/ScheduleListItemVO.java、ScheduleDetailVO.java
├─ enums/ScheduleStatusEnum.java               （1待上架 2已上架 3已取消 ＋ 两套文案）
└─ convert/ScheduleConverter.java
```

## 3.2 类与职责

| 类 | 职责 |
|---|---|
| `ScheduleController` | 管理端请求、校验、装配响应；**不写业务规则** |
| `SchedulePublicController` | 用户端免登录查询（`@Anonymous`），只读 |
| `ScheduleService` / `ScheduleServiceImpl` | 四项关联校验、教室归属校验、时间与人数校验、**14 天窗口**、**两条冲突校验**、**状态流转门禁**、**删除门禁（仅待上架）**、事务边界；并**对外**提供 ①四个 `countActiveByXxx(...)`（供主数据删除门禁）②用户端查询方法（**全项目统一不另立 QueryService**） |
| `ScheduleDao` / `ScheduleDaoImpl` | 组装筛选、分页、稳定排序；**区间相交查询**、**完全同时段查询**、**四类门禁统计** |
| `ScheduleMapper` | 继承 `BaseMapper<ScheduleDO>` |
| `ScheduleDO` | 与 `t_schedule` 对应；**无逻辑删除字段** |
| `ScheduleCreateDTO` / `ScheduleUpdateDTO` | 新增／修改入参（不含 `status`、`bookedPersons`） |
| `ScheduleQuery` | 列表筛选与分页 |
| `ScheduleListItemVO` / `ScheduleDetailVO` | 接口出参 |
| `ScheduleStatusEnum` | 状态码、**"已结束"的推导**，以及**两套状态文案**（管理端：待上架／已上架／已取消／已结束；用户端：可约／已结束／已取消）——都收在这一个枚举里，避免多处各写一遍 |
| `ScheduleConverter` | DTO、DO、VO 转换（含跨模块名称补齐后的装配） |


# 4、运行流程

## 4.1 查询列表
1. Controller 校验 `ScheduleQuery`（`pageSize` 上限 100、`status` ∈ {1,2,3,4}；按存储状态筛选）。
2. Service 调 DAO 分页查询（**日期区间直接筛 `schedule_date`**），按 `update_time DESC, id DESC` 排序（管理端列表；用户端排序见用户端接口详细设计）。
3. Service 批量调 `StoreService` / `CourseService` / `CoachService` / `ClassroomService` 补齐名称（**按 ID 去重后批量查，避免 N+1**）。
4. Service 用 `ScheduleStatusEnum` 推导 `statusText` 与 `finished`，转 VO 返回。

## 4.2 查询详情
1. Service 按 ID 查询；不存在 → `404`。
2. 补齐四个对象的名称，推导状态文案，返回。

## 4.3 新增排课

1. Controller 校验必填、ID 与时间格式。
2. Service 开启数据库事务。依次通过 `StoreService.lockByIdsForUpdate`、`CoachService.lockByIdsForUpdate`、`CourseService.lockByIdsForUpdate`、`ClassroomService.lockByIdsForUpdate`，锁定门店、教练、课程、教室行（按主键执行 `SELECT ... FOR UPDATE`）。锁一直持有到事务提交或回滚；关联对象不存在返回 `404`。跨模块只调用对方 Service，锁方法加入调用方同一个事务，不能开启独立事务或提前释放锁。
3. 在锁内以当前读重新检查门店、课程、教练、教室存在，且教室归属目标门店；校验 `startTime < endTime`、同一自然日、`maxPersons > 0`、`1 <= minPersons <= maxPersons`，以及上课日期处于 `Asia/Shanghai` 今天起 14 天内（含今天）。
4. **重复排课检查**：不存在同一门店、同一课程、完全相同起止时间且 `status <> 3` 的其他排课。锁内使用当前读查询匹配行（如 `SELECT id ... LIMIT 1 FOR UPDATE`），查到返回 `409`：“该门店该课程在此时间已有排课”。门店行锁使同一门店内这类检查与写入串行执行，即使两个请求选择不同教练，也不会同时通过重复检查。
5. **教练时间冲突检查**：查询同一教练、`status <> 3` 且满足 `已有 start_time < 新 endTime AND 已有 end_time > 新 startTime` 的排课，使用当前读；查到返回 `409`：“该教练在此时间段已有排课”。时间区间按左闭右开处理，上一节结束时间等于下一节开始时间允许相接。同一教练行锁覆盖其跨门店排课，不依赖冲突记录已经存在，因此首次同时新增也能互斥。
6. 所有校验通过后，从课程复制 `course_type` 作为课种快照，由 `start_time` 推导 `schedule_date`，写入 `status = 1`、`booked_persons = 0`；主键与审计字段由公共机制处理。
7. 提交事务后释放关联对象行锁，返回统一成功响应，不返回新 ID。等待锁的后续请求取得锁后重新检查最新数据，不能沿用等待前的普通查询结果。

**写操作共同约定：** 锁顺序固定为“门店 ID 升序 → 教练 ID 升序 → 课程 ID 升序 → 教室 ID 升序 → 排课 ID”；通过对应 Service 按该顺序逐行加锁。事务内不调用短信、外部 HTTP 等耗时服务。数据库死锁或锁等待超时须先回滚，再从事务外最多重试 2 次完整事务；业务冲突 `409` 不重试，仍失败返回 `409`：“排课正在被其他操作修改，请稍后重试”。不能在已失败的事务内重试 SQL。修改、状态流转、删除和结束状态定时更新也须遵循同一锁协议。主数据删除在本模块对应对象行锁内执行引用当前读统计并删除，主数据已被历史排课引用但允许删除时，后续历史展示仍使用空值兜底；终态写请求直接拒绝，不因加锁而要求恢复已删除主数据。

## 4.4 修改排课

1. Controller 校验排课 ID、必填字段与时间格式。Service 先读取排课的原门店、原教练、原课程、原教室作为待加锁对象，不存在返回 `404`；这次预读只用于确定锁集合，不作为最终编辑依据。
2. 开启数据库事务，收集原／新门店、原／新教练、原／新课程、原／新教室，按每类对象分别去重。严格按“门店 ID 升序 → 教练 ID 升序 → 课程 ID 升序 → 教室 ID 升序 → 当前排课行”顺序，通过对应 Service 逐行 `SELECT ... FOR UPDATE` 加锁；未更换对象时只锁一次。新关联对象不存在返回 `404`。
3. 锁定当前排课行后进行当前读，重新检查存在性、原门店／教练／课程／教室及编辑门禁。若门店、教练、课程或教室已与预读值不同，说明并发操作改变了锁集合，本次回滚，从重新预读开始有限重试；不能在持有部分锁时追加不符合顺序的新锁。确认排课仍可编辑（待上架）后继续，非待上架返回 `409`。
4. 在锁内执行新增流程第 3～5 步的关联、时间、人数、日期窗口、重复排课与教练区间相交校验；两类冲突查询均增加 `id <> 当前 scheduleId` 排除自身。使用当前读重新获取冲突结果，不复用预读快照。
5. 更换课程时刷新课种快照，开始时间变化时刷新 `schedule_date`。显式更新允许编辑的业务列，不覆盖 `status`、`booked_persons`；组装最新 `ScheduleDetailVO`。
6. 提交事务并释放全部行锁，返回最新详情。并发修改、死锁与锁等待失败按新增流程的有限重试约定处理；业务校验不通过直接返回，不自动覆盖其他请求的最新状态。

## 4.5 状态流转
1. Service 预读排课及关联 ID，不存在返回 `404`，已取消／已结束的终态请求直接拒绝。对可操作排课开启事务，按 §4.3 的关联对象、排课行锁顺序加锁并当前读；重新检查存在性与状态，锁集合发生变化时回滚并有限重试。这样取消等状态变化不会绕过新增／修改的冲突锁协议。
2. `status ∈ {3,4}` 或（`status = 2` 且 `end_time < 当前时间`）→ `409`（终态）。
3. 目标 = 当前 → **直接按成功返回**（幂等）。
4. 校验合法流转（`1→2`、`2→1`、`2→3`）；非法 → `409`。
5. 只更新 `status` 列；返回统一成功响应。

## 4.6 删除排课
1. Service 预读当前门店与教练，开启事务，按 §4.3 的门店、教练、排课行锁顺序加锁并当前读；不存在返回 `404`，锁集合发生变化时回滚并有限重试。
2. `status != 1` → `409`（已上架须先下架；已取消与已结束不可删）。
3. 执行 `DELETE`。

---

## 4.7 结束状态定时维护（后续交付）

1. 后续增加定时任务，以 `Asia/Shanghai` 当前时间作为本轮截止时间，分批扫描 `status = 2 AND end_time < 本轮截止时间` 的排课。按用户确定的严格小于比较，不把恰好等于截止时间的记录提前结束。
2. 每条记录使用短事务，按 §4.3 的公共锁顺序锁定仍存在的关联对象，再锁定排课行并当前读；历史主数据已删除时跳过缺失的关联行，不阻止结束状态落库。
3. 锁内再次确认状态仍为已上架、结束时间已到，条件更新 `status = 4`；已取消、已结束及其他状态不更新。与取消操作竞争时以锁内最新状态为准，不将已取消改成已结束。
4. 提交后处理下一条；按 §4.3 对明确回滚的死锁／锁超时有限重试，失败留待下一轮扫描。重复扫描不改变已经结束的记录。
5. 任务频率和每批数量在任务交付时确定。在任务上线前，“已结束”筛选及状态 4 的自动维护尚未完整交付；任务间隔内的展示可以按结束时间兜底，但不得将所有查询接口变成隐式状态写入入口。
