**用途：** 记录详细设计的**评审意见、设计决策与变更原因**。设计正文在 `详细设计.md`，本文件只记过程与理由，回答「为什么这么设计」「谁提的、什么时候改的」。

**约定**

| 项 | 说明 |
|---|---|
| 记录范围 | 只记**已生效**的评审意见与决策；尚未拍板的待确认项在 `详细设计.md` 的 1.4（字段）与 2.5（接口）里，不进本文件 |
| 一条记录包含 | 时间 / 来源 / 意见 / 处理 / 理由 / 影响文件 |
| 与正文的关系 | **正文是唯一权威**；本文件不复制正文内容，只留理由与变更轨迹 |
| 同步要求 | 正文改了，这里必须同步登记一条；不要只改正文不记录 |

## R06（2026-09-22）日志设计的两条口径

| 项 | 内容 |
|---|---|
| 来源 | 编写第 6 章时的设计判断（需评审） |
| 口径一 | **查询类接口不写业务日志**。查询是高频只读操作，逐次埋点会淹没需要审计的写操作；「谁查了什么、耗时、状态码」由公共模块的统一访问日志覆盖。仅保留慢查询（建议 500 毫秒）WARN |

## 由 R01~R03 归纳出的活动图口径

已写进 `详细设计.md` 第 4 章章首：

> **画什么：** 活动图只画**业务步骤与其落表操作**。横切基础设施（全局异常处理）与框架自动行为（主键生成、审计字段填充）不属于业务步骤，不出现在活动图里。表操作保留 —— 模板明确要求活动图体现「类与**表**之间的交互」。
>
> **怎么写：** 泳道标题可以用类名或表名；**泳道里每一步用中文业务语言描述，不写方法名、不写 SQL、不写框架名**。

两条判据：

1. **这一步是不是「这个功能要实现的事」？** 是 → 画；只是「框架顺手做的事」或「全局兜底的事」→ 不画。
2. **这行字是给业务看的还是给代码看的？** 「谁做」用类名（泳道标题），「做什么」用中文（泳道内容）。
