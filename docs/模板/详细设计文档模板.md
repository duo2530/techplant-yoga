# 2、接口

> **指引**
> 只写**本模块对外的接口**（三端调服务端、服务端调第三方）；**跨模块调用的接口写在第 3 章**，不要混进来。
> 先想清这个模块**实际有哪些接口**，再动笔 —— 数量、HTTP 方法、路径形态、是否分页、有无请求体，全部由模块决定，**不要套增删改查的套路**。
> 每个接口按「方法与路径 → 说明 → 请求参数 → 请求/返回示例 → 返回结果 → 返回数据结构」写；**用不到的段落直接删掉**，不为凑格式硬写。

# 5、测试用例设计

> **指引**
> 每条用例按**四要素**写：**（1）数据准备 →（2）输入 →（3）输出 →（4）资源清理**。
> **覆盖要求**：每个类都要有测试类、每个方法都要有用例；用一张覆盖表把「类 → 方法 → 用例编号」对应起来，让人能核对有没有漏。
> **排序**：大类按「业务实现类 → 接口层 → 数据访问层 → 转换层」；类内部按「**正常分支 → 边界 → 异常分支**」；**同一方法的用例必须相邻**。
> 用**中文业务语言**描述用例，**不写测试代码**；关键数据给具体值，便于直接转成测试方法。
> **怎么推用例**（按顺序）：① 取被测类与公开方法；② 每个方法切正常值 / 边界值 / 非法值；③ 把第 2 章每个接口的**非 200 状态码**逐个变成异常用例；④ 补**契约锁定用例** —— 锁住「实现者容易违反、且违反了不容易发现」的约定，这类价值最高；⑤ 真实 SQL 与跨模块真实调用**不进单元测试**，放冒烟测试。
> 单元测试用模拟对象隔离、不连数据库；冒烟用例**必须能自己清理数据**。

# 6、日志设计

> **指引**
> 回答「出问题时靠什么日志定位」。
> **查询类接口不写业务日志** —— 高频只读日志会淹没需要审计的写操作，交给公共模块的统一访问日志；只保留慢查询告警。
> 每条埋点写清**四件事**：触发时机、级别、内容（字段）、用途。级别口径：INFO = 写操作成功；WARN = **可预期的业务失败**（参数校验失败、对象不存在、门禁拦截、跨模块调用失败）；ERROR = 非预期异常；DEBUG = 跨模块细节，默认关闭。
> 修改类记**变更字段的前后值**且**只记变化了的**；状态流转记**原状态 → 新状态**；**门禁拦截单独埋一条 WARN 并带上阻塞明细** —— 这是唯一「用户会来问为什么」的分支。
> 长文本字段、完整附件地址、请求全量报文不写进日志。
