# 活动清单（实施顺序与验收门禁）

**文档版本：v2.1（重置版）**（2026-10-01）

**用途：** 记录一期功能实施的**先后顺序、依赖关系、交付物、验收点与状态**，并作为「**先评审详细设计、再动手实施**」的执行依据。

**维护口径：**

1. **顺序即实施顺序** —— 按本清单从上到下推进；每个活动**开工前先确认它依据的详细设计文档**，确认后才进入实施。
2. **同阶段内可并行** —— 阶段是串行的，阶段内的活动（如阶段一的四项基础数据）互不依赖，可并行推进。
3. **进度只在本文件维护** —— 详细设计文档只写设计，不记进度与排期。
4. **一处一改** —— 实施中发现文档与实现冲突时，**先改文档、再改代码**（文档驱动）。
5. **设计决策记在《详细设计总览》§5** —— 本套文档**不单独建"设计记录／评审记录"**，需要长期留存的结论集中登记在 [`../详细设计/详细设计总览.md`](../详细设计/详细设计总览.md) 的**关键设计决策登记**表里。

| 状态 | 含义 |
|---|---|
| 未开始 | 尚未确认该活动的详细设计 |
| 设计中 | 正在按详细设计核对／补充 |

| 验收中 | 代码完成，正在按验收点核对 |

# 0、总体顺序

```text
阶段一 · 基础数据（四项并行）
    门店管理 ┐
    教室管理 ├──→  阶段二 · 排课管理  ──→  阶段三 · 用户端三页
    教练管理 ┤                            （首页 / 约课页 / 课程详情页）
    课程管理 ┘
    阶段四 · 管理端登录与菜单（横切，随时可做）
```

**为什么阶段一必须四项并行：** 排课**同时引用门店、课程、教练、教室四者**（`t_schedule` 的 `store_id` / `course_id` / `coach_id` / `classroom_id` 全部必填，`BR-排课-001`），少任何一项排课都录不进去，因此四项并行完成、互不阻塞。

**为什么教室必须在排课之前：** 排课要校验「**教室存在，且归属门店 ＝ 排课门店**」（`BR-教室-005`、`BR-排课-006`）；反过来，门店删除门禁要统计「**名下教室数**」（`BR-门店-009`）。两者互为依赖，实施时**教室侧先用「接口 ＋ 临时实现」占位**，两侧都落地后接真实实现。

# 6、横切事项（所有活动共用）

| 事项 | 约定 |
|---|---|
| **删除方式** | 一期 **5 张业务表一律物理删除**：不建 `deleted`、不用 `@TableLogic`（见 [详细设计总览 §5 决策 1](../详细设计/详细设计总览.md)） |
| 菜单 ID 分配 | **沿用既有一级目录 `2000`「经营基础」**（与若依自带「系统管理」目录并列）：`2001` 课程管理 / `2002` 教练管理 / `2003` 门店管理 **保留**；`2004` **排班管理 → 改名「排课管理」**；**新增 `2006` 教室管理**；`2005` 预约管理**暂留**（一期不接入口）。**若依自带的「系统管理」菜单完全不动** |
| 响应与业务码 | HTTP 固定 200；业务码 `200/401/404/409/500`；**`@Valid` 失败是 500**（框架既有行为，本期不改）；409 明细拼在 `msg` 里 |
| 枚举返回 | **码与名称必须成对返回**：`courseType`＋`courseTypeName`、`regionCode`＋`regionName`、`status`＋`statusText`；**前端不维护码→名映射** |
| ID 序列化 | 字段名为 `id` 或以 `Id` 结尾的 `Long` 自动转字符串 |
| 分页 | `Query` 对象 ＋ MyBatis-Plus `IPage` → `PageResult` → `TableDataInfo`；**必须有稳定排序**；上限 100 |
| 跨模块调用 | **不跨模块读表、不另立 QueryService**；一律直接依赖对方模块的 Service；调用失败 **fail-closed** |
| 数据库 | 建表语句与示例数据统一进 `backend/sql/yoga.sql`；**不做增量 SQL**（只给最终结构） |
| 权限 | 一期**不做 RBAC**；管理端接口只要求登录，**不发明权限串** |
| 文档同步 | 实施中若发现文档与实现冲突：**先改文档、再改代码**；新决策追加到《详细设计总览》§5 |
