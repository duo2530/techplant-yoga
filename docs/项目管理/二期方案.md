## 1. 现状盘点（事实）

### 1.1 一期已完成

管理端「经营基础」五模块（门店／教室／教练／课程／排课）＋ 用户端三个免登录只读接口（`/api/stores`、`/api/schedules`、`/api/schedules/{id}`），共 28 个接口、5 张业务表。一期验收口径是「**能看**」，**不产生任何预约、会员、会员卡数据**。

### 1.2 二期要接的东西现在长什么样

| 对象 | 代码/数据现状 | 结论 |
|---|---|---|
| 预约模块 | `ruoyi-yoga` 里 `booking` 模块**代码齐全但不可用**：`ScheduleBookingSupportImpl` 直接抛「一期暂不开放预约功能」；`BookingServiceImpl` 仍用旧字段 `capacity`/`bookingCount`；`BookingMapper.xml` 查 `s.deleted`/`s.status=1`，与新 `t_schedule` 列不符；`BookingDO` 仍带 `@TableLogic` | **是"重构"不是"新建"**，必须先做存量对齐 |
| 预约接口 | 管理端 3 个已存在（`/admin/bookings`、`/{id}`、`/schedule/{id}`）；用户端 3 个已存在但 `POST /api/bookings` **未标 `@Anonymous`** → 当前必然 401 | 路径可复用，鉴权与实现要重做 |
| 数据表 | `yoga.sql` 只有 `t_store`/`t_classroom`/`t_coach`/`t_course`/`t_schedule`；**无**会员、会员卡、账号、订单、支付表；`t_booking` 声明不建 | 二期需新建 5 张表 |
| 用户端登录 | **假登录**：`api/auth.js` 验证码写死 `8888`，返回 `mock-token-wechat`/`mock-token-phone`；`pages/auth/*` 三页只调它 | 需真实账号与鉴权体系 |
| 用户端「我的」 | `profile`/`my-bookings`/`my-trials`/`activities`/`messages` 等页全部走 `uni-app/mock/**` 假数据 | 二期逐个替换为真实接口 |
| 用户端鉴权 | 只有 RuoYi JWT 一套；`/api/**` 靠类上 `@Anonymous` 免登录，其余走 `sys_user` | **二期最大架构决策点**：会员端账号与 `sys_user` 的关系 |
| 联调配置 | 管理端走 vite 代理 `/dev-api`；用户端 `config.js` 直连 `http://localhost:8080`，无代理、无 env；用户端是 HBuilderX 工程**无 package.json** | 联调方式与一期不同，需单独安排 |

### 1.3 一期已预留的衔接点（好消息）

- `t_schedule.booked_persons`（已预约人数）**已建表并固定为 0**，二期接预约**不需要改表**，只需让它随预约增减。
- 排课的「已结束」判定已在 service 层按 `end_time <= now` 推导，取消预约的时限规则可以直接复用这个时间口径。
- 用户端接口契约（`AjaxResult`/`TableDataInfo`、枚举成对返回、雪花 ID 转字符串）已定型，二期沿用。

### 1.4 二期的最大风险：业务口径空白

《业务规则》v2.1 的 70 条里**没有一条**涉及会员、会员卡、登录认证、预约/取消、排队、扣次——它们被 `BR-全局-005` 整体排除在二期之外。现有描述只散落在**旧版清单/信息结构图**（已声明不作依据）和**真实 App 实测**里：

- 会员卡类型：只有 **次数卡、年卡**（无储值卡、期限卡，无冻结/转让/退卡字样）
- 会员卡字段：初始次数、当前剩余次数、卡号、卡片类型、卡片名称、卡片状态（**只有"未开卡/过期"**）、有效期
- 预约单字段：卡类型（会员卡/体验卡）、卡种、课种、预约状态（**只有"已预约/已取消/已签到"**）
- 场次字段：不可取消预约时间、排队上限、停止排队加入预约时间
- **扣次/返次没有任何字段或规则定义**

> **因此本方案的第一波不是写代码，而是补文档**——这与项目「文档先行、先改文档再改代码」的硬约束一致（`一期开发路线图.md` §0）。

## 2.1 用户表与会员表的职责划分（D2 已确认方案）

**一句话结论：登录账号放 `t_user`，业务档案放 `t_member`，会员卡与预约都绑会员。**

> **2026-10-02 确认的三项：** 用户表命名 **`t_user`**；`t_member.user_id` 建**唯一索引**（严格一对一）；**两表同属一个模块**（便于"会员列表按手机号筛选"直接联表）。

### 2.1.1 字段归属

| 关注点 | 放哪张表 | 理由 |
|---|---|---|
| 手机号（**登录标识**，唯一） | **用户表** | 登录用；换号/换绑只动这张表，不影响业务档案 |
| 密码哈希 | **用户表** | 允许为空（前台先建档、会员后续设密） |
| 微信标识（openid／unionid） | **用户表** | 二期不启用，预留列 |
| 昵称、头像 | **用户表** | 属"账号资料"——真实 App 的「设置」里改的正是头像/用户名 |
| 账号状态、最后登录时间 | **用户表** | |
| 真实姓名、性别、生日 | **会员表** | 业务档案 |
| **会员等级 `level`** | **会员表** | 从 V0 普通会员起（真实 App 未登录态展示的就是 `V0 普通会员`） |
| **会员状态**（正常/停用） | **会员表** | 与账号状态是**两件事**：账号停用＝不能登录；会员停用＝不能开卡/预约 |
| 归属门店（可空） | **会员表** | 二期可先不做 |
| 会员卡 | **绑会员**：`t_member_card.member_id` | 扣次是会员的属性 |
| 预约 | **绑会员**：`t_booking.member_id` | 占名额、扣次都是会员的属性 |

### 2.1.2 关系设计

- 二期：`t_member.user_id → t_user.id`，**一对一**（在 `user_id` 上建唯一索引）——**已确认**。
- **表结构天然支持一对多**：将来要"一个手机号 = 家长 ＋ 孩子"这类场景，只需去掉那个唯一索引，**不必改表**。
- 命名：**`t_user`（C 端用户账号）** 与 **`t_member`（会员档案）**——**已确认**。注意与管理端若依自带的 **`sys_user`** 区分，两者互不相干，必须在详细设计里写明，避免后人误用。

### 2.1.3 两条建档流程（解决"密码从哪来"）

| 场景 | 流程 |
|---|---|
| **前台办卡（管理端）** | 录入手机号 → 建 `t_member`；若该手机号还没有用户账号，**同时建一个无密码的 `t_user`**，会员的 `user_id` 指向它。会员之后用"手机号＋验证码"登录，**首次登录时设置密码** |
| **C 端自助注册** | 手机号＋验证码＋密码 → 建 `t_user`，**并自动建一条 `t_member`（等级 V0 普通会员）**；若该手机号**已被前台建档**，则**绑定已有会员档案**，不新建、不覆盖 |

> 这样"管理端先建会员、用户后来才注册"和"用户先注册、之后才办卡"两条路都能走通，且**手机号始终是唯一的收敛点**。

### 2.1.4 模块划分

两张表**放在同一个业务模块**内（`ruoyi-yoga` 下同一个包）——**已确认**。这样"会员列表按手机号筛选"可以直接联表；若拆成两个模块，则按一期约定「**不跨模块读表、依赖对方 Service**」，需要账号模块额外提供批量手机号查询，成本更高。
