# 并发反例与实现机制

本文件采用 [模型 A01](02-领域模型与不变量.md)：关闭排课后系统取消、释放有效占位并返原扣次。所有系统取消交错都是设计分析，当前没有对应生产入口。事务图中的“错误版本”用于反例，不表示当前代码必然这样执行。

## 1. 用读写集筛选冲突

操作集合 `C=Create`、`U=MemberCancel`、`S=ScheduleCancel`。S 内含排课关闭与全部符合条件预约的取消。`P/M/R/K/L` 分别是排课、会员、预约、卡和流水；`I` 是请求意图。读写集以同一实体身份为交集，不是表名相同就一定冲突。

| 操作 | 决策读取 | 提交写入 | 串行化支点 |
|---|---|---|---|
| C | P状态/容量/时间、M存在性、K资格/余额、I、同会员同排课active记录 | R、P计数、次数卡K/L | 同P行锁；跨P同卡受K锁；当前还受M锁 |
| U | R归属/状态/快照、P状态、原扣次L、K | R、P计数、K/L | P→R→K |
| S | P状态/关闭原因、全部R状态、各原扣次L/K | P关闭、各R/P计数/K/L | 小规模一次事务 P→按id的R→按id的K |

无序两两组合只有六种，不需要枚举用户身份×网络×所有状态的全笛卡尔积：

| 对 | 共享实体等价类 | 首要性质 | 必要代表交错 |
|---|---|---|---|
| C/C | 同P异M；异P同K；同M同键；同M同P异键；完全独立 | I1/I3/I5/I8 | 最后名额、最后次数、重放、重复有效预约 |
| C/U | 同P同M旧预约；同卡异P；不相交 | I2/I6、重约顺序 | 取消提交前重约不能把旧预约当不存在 |
| C/S | 同P；异P同卡；不相交 | 关闭准入和返次闭环 | 谁先取得P锁决定是否先创建再被取消 |
| U/U | 同R；同P异R；同卡异P | I4、计数和余额不丢更新 | 同一扣次只返一次 |
| U/S | 同R；同P其他R；不相交 | I4、取消原因归属 | 先提交者保留原因，后者零副作用或补处理剩余 |
| S/S | 同P同事件；不同P同卡 | 幂等和可恢复 | 任务重启不漏返，也不重复返 |

再对每种迁移插入故障断点：取得锁前、插预约后、更新人数后、扣返余额后、写流水后、COMMIT前、COMMIT后响应前。每个断点只需检查“整事务未提交”与“已提交但客户端未知”两个核心等价类；死锁和超时另检查回滚范围。这比凭经验列几十种“网络异常场景”更可控。

## 2. 具体事务交错与正确结果

以下 `T1/T2` 为独立数据库连接，初值显式给出；`wait` 表示实际等待需由锁观测确认。并发正确结果允许合法的多个串行顺序，不要求固定某个用户必胜。

### H1 两个人抢最后一席：绝对值条件的陷阱

初值 C=1、B=0，用户和卡不同，各 p=1。错误版本只普通 SELECT 再绝对值 UPDATE：

1. T1 SELECT B=0，计算 newB=1。
2. T2 SELECT B=0，也计算 newB=1。
3. T1 INSERT R1；UPDATE P SET B=1 WHERE C>=1；COMMIT。
4. T2 INSERT R2；UPDATE P SET B=1 WHERE C>=1；COMMIT。

结果 B=1，却 Σactive p=2，破坏 I1/I2。即使 T2 更新报告 0 行“实际变化”，也不能把客户端驱动 affected rows 语义作为业务保护。**当前代码以 P FOR UPDATE 防止此交错；`max_persons>=newB` 本身不是充分条件。** 正确版本 T1锁P，T2等待；T1提交后T2读B=1拒绝，最终仅一预约、一扣次。

### H2 同卡预约两个排课

初值卡 b=1，P1/P2各有空位，各 p=1。错误：T1/T2都读b=1，各写b=0并各有D=-1，最终余额0但期初1＋流水-2=-1，I6已破坏，即便没有负余额。

正确：各先锁自己的P；T1取得K锁扣1；T2等K，T1提交后见b=0拒绝并回滚其P/R变化。若用 `b=b-1 WHERE b>=1`，第二个写在锁后不匹配，返回0；整事务回滚。当前同会员还受M锁串行，故现有同卡测试不能单独证明去M锁后仍正确，必须另测隔离机制。

### H3 相同意图重试、以及同排课不同意图

初值同会员键 k不存在，C=1。T1创建k占满，提交前暂停。T2先普通读建立RR快照，看不到k，然后等待P锁。T1提交。若T2拿锁后先校验容量，会错误返回满额；若用普通读复查仍可能看不到k。正确是先当前读复查k、比参数、按原意图成功。现有 `create_retryWithOldSnapshot_shouldReturnSuccessEvenWhenFull` 针对这一反例。

若T2用同键但换P/card/p，必须冲突，不是成功重放。若换新键但同P同会员，不能产生第二条active记录；必须当前读检测active，或由活跃唯一键拒绝。取消后的新键允许重约；旧键仍只能指原已取消记录。

### H4 会员取消和系统取消同时到达

初值R=RESERVED、p=1、D=1，P开放。错误：T1和T2都读“未取消”；T1返1、T2返1；后者覆盖取消原因，I4失败。

正确 A01：两者都从P锁开始。若U先提交：R取消/MEMBER、返1、B减1；S随后关闭P，跳过该R，不再返。若S先提交：P关闭、R取消/SCHEDULE、返1、B减1；U取锁后先见R已取消，返回成功重放。最终都只返一次；取消原因由首个有效转换保留。若S看到已签到，按A04整事务拒绝，不能部分返完后再检查已签到。

### H5 取消与重新预约

初值同会员同P有Rold，容量1。T1取消；T2用新键创建。U先持P并提交，则T2见无active、B=0，创建Rnew成功，卡经历返1再扣1。C先持P则因Rold仍active拒绝；U之后成功。两个顺序都合法，不要求T2自动等待“将要发生”的取消。旧键创建重放只返回旧意图，不会生成Rnew。

补充同卡异P：T1取消P1并返次，T2创建P2。可售资格按K锁获取后的余额决定；不可提前读取后无条件写余额。

### H6 创建与关闭排课

初值P开放、无预约。推荐S和C都先锁P。

- S先：关闭并提交，C当前读见关闭，拒绝且无扣次。
- C先：创建提交，S随后看到新R，同事务关闭、取消并返次。最终P关闭、B=0、R取消、D/R相抵。

**当前只实现前一半边界保护**：关闭先提交会阻止后续创建，但创建先提交后 `changeStatus` 不扫预约。最终P已取消、R仍已预约、卡仍被扣，业务闭环未完成。仅测试“关闭先提交”不能证明取消排课正确。

另一个观察：`changeStatus` 先普通读状态、最终 `UPDATE WHERE id`。T1读已上架打算下架，T2先取消并提交，T1随后写待上架可能覆盖终态。应在同P锁内验证或 `UPDATE ... WHERE status=expected` 并检查行数。这是源码推导的反例，尚无实测，且与预约锁之外的写入口有关。

### H7 提交成功、客户端超时

T1执行全部写入→MySQL COMMIT成功→响应链路丢失；客户端仅知道UNKNOWN。T2以原k、原参数重试，唯一键＋当前读返回原意图，不新增R/P/K/L。最终只有一次效果。若客户端换键且原预约已取消，可能合法创建新预约，因此“同会员同排课不能重复”不能替代意图幂等。

若COMMIT是否到达DB未知，允许成功或回滚两种最终状态；检测器需尝试将未知操作解释为生效一次或未生效，再以主库查询与后续重放缩小范围。不能把所有超时当失败，也不能强行补偿。

### H8 中途异常、死锁、锁等待超时

T1插R→改B→扣K→写L抛SQL异常；异常越过事务代理，整体回滚，四表均应等于操作前。取消同理。现有用临时CHECK拒绝特定流水类型的测试适合验证这一点。

死锁反例用两个资源：T1锁P1→等P2；T2锁P2→等P1，MySQL选一个事务回滚。正确结果是获胜者完成，受害者整体回滚，若重试则在**新的**事务执行完整意图。锁等待超时默认语句级回滚，应用不得捕获后继续提交已插R；应让异常越过最外事务或显式标rollback-only。

当前创建P→M→K、取消P→R→K的局部顺序不能证明全图无环。幂等不存在键的范围锁、活跃查询扫描、管理修改、批量多卡和多排课都可能增加边。要收集真实 deadlock graph，不用“所有地方有锁”作无死锁结论。

### H9 定时任务中断再执行

推荐小规模单P单事务：T1锁P→关闭→取消R1/返次→进程中断，未提交则数据库回滚；重启整P重做。若已提交但未记录任务完成，重做从状态及流水检查得到零副作用。不能在关闭P后单独提交，再把“P已经关闭”作为不继续取消R的依据。

若单P事务过大才考虑分批：关闭准入先提交，持久保存取消事件；逐预约用事务转换与返次，最后核对无未处理记录才完成。此时“关闭后预约最终清理”是明确的最终一致性契约，期间不能宣称全部返次已完成。游标越过失败记录、仅扫描OPEN排课、只按一次任务内存列表恢复都会漏返。该架构是可选方案，未实现且未测试。

## 3. 机制比较：每个机制只承诺自己的部分

| 机制 | 能维持的性质 | 必要条件／索引 | 不能解决／代价 |
|---|---|---|---|
| 条件原子UPDATE | 单行容量或余额下界；状态CAS获胜者 | 事务内检查affected rows；id主键＋合法正数；资格一起写入WHERE或在同锁内检查 | 不自动联动R/L，也不记忆已处理意图；同一热点行仍串行等待 |
| `SELECT FOR UPDATE` | 读取最新可修改版本并锁内多步决策 | 显式事务；命中适当索引；所有相关写者遵循协议；取得锁后复查 | 不会让普通读自动变当前读；不存在的键不等于锁住业务实体；范围可能有gap/next-key锁 |
| 唯一索引 | 意图键、流水至多一笔、可选活跃预约唯一 | 正确列域／NULL／排序规则；冲突时整笔事务语义明确 | 只能限制行是否存在，不能证明余额对应流水；冲突可能锁等待/死锁 |
| CHECK、NOT NULL、FK | 单行合法范围、引用存在 | MySQL≥8.0.16执行CHECK；FK索引；迁移前清查 | CHECK不做跨表SUM；FK不表达“只能已上架时预约”；增加写成本和删除约束 |
| 版本号乐观锁 | 读后写未被别人改变（比较并交换） | 每个写入口都维护version；UPDATE带原version；失败重读整个决策 | MySQL更新仍加锁；热点重试多；遗漏某个写入口即失效；不替代跨表事务/幂等 |
| 悲观锁 | 多条件决策和前置资格稳定 | 即上述行锁协议，不是额外一种神奇机制 | 更长持锁时间、连接占用、死锁；不能把网络调用放锁内 |
| 状态条件迁移 | 同R仅一请求获取消资格 | `WHERE status=RESERVED`，返回1才返次；同事务写R/K/L/P | 状态获胜但返次异步失败仍不完整；不能单靠status鉴别未知提交 |
| 幂等键＋参数绑定 | 同一意图最多一次有效副作用及可重复取得结果 | 稳定身份、唯一键、不可变payload、保留历史；必要时结果查询 | 不保证不同键没有业务重复；当前失败未留键，不能声称失败结果永久一致 |

依据：MySQL E05–E10、Spring E11。RR并不等于串行化；换成RC可减少部分范围锁，但不免除正确条件写、唯一约束、事务和幂等。未运行前不建议为了简化推理直接切隔离级别。

## 4. 当前场景的最小实现选择

保留现有单库本地事务、P/M/K行锁与请求／流水唯一键；不同时移除M锁、改隔离级别和改变取消语义。先补关闭后的预约返次语义与状态写入口保护。无需分布式锁、消息队列或新微服务。

### 创建：可审查的SQL边界

下列 `:name` 是绑定参数，供Mapper/JDBC改写，不能直接复制为MySQL终端语法。示意省略审计列，生产插入复用原DAO，不能维护另一套业务SQL测试副本。

```sql
START TRANSACTION;
SELECT * FROM t_schedule WHERE id=:schedule FOR UPDATE;
SELECT id FROM t_member WHERE id=:member FOR UPDATE;
SELECT * FROM t_reservation
 WHERE member_id=:member AND request_id=:request LIMIT 1 FOR UPDATE;
-- 应用：已存在则比对payload并返回原意图；否则校验排课资格
SELECT * FROM t_member_card WHERE id=:card FOR UPDATE;
SELECT id FROM t_reservation
 WHERE schedule_id=:schedule AND member_id=:member AND status IN (1,3)
 LIMIT 1 FOR UPDATE;
-- 应用：校验卡资格、persons域和没有有效重复
UPDATE t_schedule SET booked_persons=booked_persons+:p
 WHERE id=:schedule AND status=2 AND booked_persons+:p<=max_persons;
-- affected rows必须为1；日期资格已在同一P锁内检查
UPDATE t_member_card SET remaining_times=remaining_times-:p
 WHERE id=:card AND member_id=:member AND card_type=1 AND remaining_times>=:p;
-- 仅次数卡执行；affected rows必须为1
-- INSERT原预约、扣次流水，任一失败回滚
COMMIT;
```

这是建议增量写法；当前源码先插预约再写绝对人数也可在同P锁前提下正确。选择增量的目的在于明确表达资源变动，而不是以为增量就能去掉所有锁。持卡锁才能准确记录before/after并稳定资格。不能给年卡跑次数UPDATE然后因为NULL返回0误判。

### 取消：只有状态转换获胜者执行资源变化

```sql
START TRANSACTION;
SELECT * FROM t_schedule WHERE id=:schedule FOR UPDATE;
SELECT * FROM t_reservation WHERE id=:reservation FOR UPDATE;
-- 应用：归属、状态、会员截止资格；系统取消走自己的资格规则
UPDATE t_reservation SET status=2,cancel_reason=:reason,cancel_time=:time
 WHERE id=:reservation AND status=1;
-- affected rows=0：按锁内读到状态区分重放或冲突，不返次
UPDATE t_schedule SET booked_persons=booked_persons-:p
 WHERE id=:schedule AND booked_persons>=:p;
-- affected rows必须为1；若0说明数据损坏，回滚并报告，不能钳制为0
SELECT * FROM t_member_card WHERE id=:original_card FOR UPDATE;
-- 读取原D校验原卡/会员；有D才按其绝对值加余额并插唯一R
COMMIT;
```

卡即使已过期或停用，当前 `lockCard` 也允许返到账面；不要调用 `lockBookableCard`，但此规则仍需Q04业务确认。原扣次缺失：年卡可不返；次数卡应作为账本异常阻断并告警，不能把所有“没流水”自动解释为无须返还。

### 系统取消：小规模整排课事务

独立Spring Bean公开事务方法，任务外层只发现候选ID且不持有覆盖整轮扫描的长事务；进入新的单排课事务后锁P重新核验触发条件与状态，按id当前读并锁相关R，先确认无已签到，再按card id固定顺序锁所有涉及卡。关闭P，转换所有RESERVED，累计释放人数，逐笔按原D返还、插唯一R；全部成功才COMMIT。原D也应使用当前读或保证其与所见R来自同一可见提交，避免外层旧快照下看得到新R却普通读不到D。当前会员取消先普通读到原R，而R和D由同一创建事务提交，具有更窄的可见性前提；不能不加分析就把该读取方式复制给批任务。

已CANCELLED的记录零副作用；已CLOSED但遗留RESERVED不能简单早退。用持久关闭原因／事件标识限定恢复范围。多卡同批要固定顺序，且禁止持K再反向取P；多排课任务一次仅处理一个P，避免批量持有多个P。即便如此仍须实测锁图和重试，不能宣称无死锁。

条件状态写示例：

```sql
UPDATE t_schedule SET status=3 WHERE id=:id AND status=2;
```

资格是在同P锁内验证的；更新0行须辨别已经完成、非法原态或资源不存在。对当前 `changeStatus` 同样补“预期状态”或锁内检查，避免覆盖终态。

### 可选数据库加固（未执行迁移）

已有锁协议可以先维持active唯一；若增加额外防线，用MySQL生成列，而非不支持的部分唯一索引语法：

```sql
ALTER TABLE t_reservation
 ADD COLUMN active_guard TINYINT
   GENERATED ALWAYS AS (CASE WHEN status IN (1,3) THEN 1 ELSE NULL END) STORED,
 ADD UNIQUE KEY uk_member_schedule_active(member_id,schedule_id,active_guard);
ALTER TABLE t_schedule
 ADD CONSTRAINT ck_schedule_capacity CHECK
   (max_persons>0 AND booked_persons>=0 AND booked_persons<=max_persons);
ALTER TABLE t_reservation
 ADD CONSTRAINT ck_reservation_persons CHECK(persons>0),
 ADD CONSTRAINT ck_reservation_status CHECK(status IN (1,2,3));
ALTER TABLE t_member_card
 ADD CONSTRAINT ck_times_balance CHECK
   (card_type<>1 OR (remaining_times IS NOT NULL AND remaining_times>=0));
```

NULL允许多条取消历史，active_guard=1限制一条有效记录。迁移前检查历史重复、非法枚举和外键孤儿；新索引会改变锁面，迁移与旧代码兼容性要在真实容器验证。还可CHECK流水符号和before/after，但跨行金额对应仍由事务和审计维持。

## 5. 原子性、隔离性、幂等性和线性化的不同责任

- 原子性：一次创建的R/P/K/L全部提交或全部回滚。
- 隔离性：并发决策看到的状态满足所用协议，防止两次都承诺同一最后资源；不是“加@Transactional就没有竞态”。
- 幂等性：同意图多次调用的可见效果等同一次；不等于不同意图必须互斥。
- 线性化目标：核心命令历史能够排成符合状态机且保留非重叠调用实时先后的合法顺序。单主库、事务代理、全体写入口遵循锁协议时，成功命令可把COMMIT作为候选生效点；这是一项需要验证的整体要求，不能从RR推出。读取旧副本或复用已建立快照的查询会影响端到端保证。
- 最终一致性：只有选择分批系统取消时，才允许关闭与返次之间有受管理的中间状态；要定义可见性、恢复与收敛期限。它不是对任意漏返的事后解释。

实现成熟度应以完整调用链、约束和反例测试判断；不按用了多少种锁计分。
