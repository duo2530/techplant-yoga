# 预约业务正确性研究

研究日期：2026-10-17。范围：创建预约、会员取消、因排课取消而系统取消预约。研究依据是当前工作区（含用户已有未提交修改），不是仅依据 HEAD。未修改生产业务实现，也未裁决尚未确认的业务规则。

## 先读结论

1. **“系统取消不释放容量”不是已确认事实，与当前 DDL 的计数定义冲突。** `booked_persons` 当前定义为未取消预约的 `persons` 总和。若预约取消却保留该值，最小反例就是容量 1、预约 1 人、系统取消：有效预约人数 0、计数 1。排课关闭可以让错误暂时不影响售卖，但不能让这个等式重新成立。
2. 推荐研究基线：系统取消先关闭排课准入，再取消未签到预约、返还原扣次、释放有效占位；历史报名人数另由历史记录计算。**这是设计建议，不是已获业务确认的新需求。** 若保留容量确实表示不可再销售的封锁量，必须单独命名和建模，不能继续称作有效占位。
3. 当前创建和会员取消已经有较完整的本地事务保护；系统取消尚无业务闭环。`ScheduleServiceImpl.changeStatus` 仅更新排课状态，会员取消又要求排课已上架，因此“先约成功，再取消排课”会留下不能由当前会员取消接口返次的预约。
4. 当前容量 DAO 是“锁内读取后写绝对值”，并非独立安全的原子增量扣减。删掉前置排课锁，仅保留 `max_persons >= 新值` 仍会丢更新和超卖。
5. 验证必须分层：业务模型是否自洽、实现是否符合模型、真实数据库是否保持约束、故障后是否可恢复。一个模型脚本通过不能替代后三层。

## 如何阅读证据状态

- **事实 F**：本次用户直接说明的背景；或经业务责任人确认并记录的规则。仓库文档不是天然等同于已确认业务事实。
- **观察 O**：当前代码或文档写了什么，含观察到的矛盾；不表示应该如此。
- **外部 E**：原始技术资料或其他项目的具体设计，只能支持其适用边界内的结论。
- **假设 A**：为了建立可检验模型而明确选取的语义，可替换。
- **未决 Q**：需要业务责任人或运行实验补充的证据，不能以技术偏好代替确认。

所有表格按所在小节给出的变量域解释；`—` 表示不适用，不能理解为任意取值。决策表按从上至下的首个匹配规则执行；描述性证据表没有执行优先级。
