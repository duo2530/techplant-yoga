# 领域模型、业务规则与不变量

来源编号见 [证据索引](01-证据索引.md)。本文件先提出可被反驳的规格，后续才讨论实现。推荐基线 A01 不是已确认业务事实。

## 1. 先把“自动取消”拆成事件

“系统”是执行者，不是足够精确的业务原因。至少有以下三种互斥语义；本次只深入第一种，不扩展其他功能。

| 事件／语义域 | 排课还能接受新预约吗 | 原预约是否继续履约 | 返次／有效占位 | 结论与来源 |
|---|---|---|---|---|
| 排课整体取消，例如停课或人数不足 | 否，关闭是前置条件 | 否 | 按原扣次返还／释放 | A01 推荐基线；人数不足触发本身 Q01 未决，当前 O09 未实现 |
| 单笔预约因资格等原因撤销，排课继续开放 | 是 | 否 | 依具体责任规则返还／通常释放 | 不属于当前已确认需求；保留计数会形成无主占位 |
| 取消预约并把名额转为运营封锁 | 可能，剩余可售减少 | 否 | 返次／有效占位释放，同时增加封锁量 | A02 替代模型：必须有封锁原因、归属和解除事件，当前无此对象 |

判定“不释放是否合理”不能只问最终能否超卖。若整个排课永不重开，保留数字可作为关闭时快照，但应命名 `closed_booked_snapshot`，且不得继续用于有效占位核对。若排课将重开，必须决定先解除哪些封锁或重新确认哪些预约，不能直接让旧数字参与售卖。

**最小矛盾**：`status=2` 的预约不参与有效人数，自动取消又把预约改成 2，同时保留 `booked_persons`。这三个命题不能同时成立；“排课已经关闭”不改变算术矛盾。

本研究选择 A01：关闭排课，取消未签到预约，释放有效占位；关闭本身阻止新售卖。这样无需新增封锁对象，也无需把预约状态和占位状态落为两个可任意组合的字段。

## 2. 对象、字段、域和关系

表中字段域是规格所需，不代表当前 DDL 都已强制。金额、优惠券、候补均不在本模型中。整数运算须限制在 Java int 与 MySQL int 范围内；生产输入上限应由容量／卡额度约束，不能只检查大于零。

| 对象／字段 | 语义与取值范围 | 来源／限制 |
|---|---|---|
| Schedule.id | 唯一正整数身份；一个排课关联 0..N 预约 | O01；核心资源应禁止被有历史预约引用时物理删除，当前保护有缺口 |
| Schedule.status | 当前持久态 1 待上架、2 已上架、3 已取消；本模型简化为 OPEN/CLOSED | O01；开始／结束时间是独立准入条件，当前代码按时间推导，文档另有 status=4 描述冲突 |
| Schedule.max_persons = C | 允许占位的人数上限，正整数 | O01；不是预约单数 |
| Schedule.booked_persons = B | 当前非取消预约人数和，非负整数 | O01；已签到仍计入；课程结束不自动清零 |
| Reservation.id、request_id | 预约身份、业务意图身份；request_id 归属会员，字符串规范化后固定，不复用 | O01/O02；当前去空格和 UUID 校验，没有显式统一大小写；DB 排序规则也影响相等性 |
| Reservation.member_id/schedule_id/member_card_id | 一次预约固定绑定一会员、一排课、一张结算卡 | O01；不因重试改变；重约创建新预约和新 request_id |
| Reservation.persons = p | 本预约占位人数，正整数且 p≤C | O02；次数卡按 p 扣次，年卡只允许 p=1 |
| Reservation.status | 1 RESERVED、2 CANCELLED、3 CHECKED_IN | O01；取消终态，结束不改预约状态 |
| Reservation.cancel_reason | 活跃时 NULL；取消后 MEMBER 或 SCHEDULE | O01；原因是事件来源，不是返还金额的替代依据 |
| Reservation.start/end | 预约时排课时间快照 | O01；排课改期后按快照还是现值取消是 Q06，当前会员取消用快照 |
| Card.type / balance b | 次数卡 type=1，b 为非负整数；年卡 type=2，次数余额不适用（可 NULL） | O01/O06；年卡没有扣返次流水，不能强行纳入次数守恒 |
| Card.initial = b0 | 开卡购入与赠送之和；模型固定初值 | A03 仅无充值、调整、迁移且无历史缺失时取 purchase+gift；其他情形需独立期初基线 |
| Ledger.reservation_id/type/delta | 扣次 D（负数）或返次 R（正数），每种至多一笔 | O01/O07；返次引用原预约扣次，原卡与会员必须一致 |
| Ledger.before/after | 在持卡锁的同一事务中变动前后余额 | O07；时间戳、雪花 ID 不一定代表卡锁获取或提交顺序 |

关系：排课 `1←N` 预约；会员卡 `1←N` 预约；次数卡预约 `1←1` 扣次、`1←0..1` 返次；年卡预约 `1←0` 次数流水。返次额度来自原扣次，不重新读取当前价格或人数计算。

**状态与占位应先在概念上分离，不一定立即拆字段。** 定义 `occupied(r)=p` 当状态为 RESERVED 或 CHECKED_IN，否则 0。只要此函数总成立，额外占位字段是冗余；若未来“已取消但封锁”等成立，就必须引入单独资源状态及其转换规则，不能让一个取消枚举承载两套矛盾函数。

实时占位 B 可增可减；累计报名 `G=Σ全部已成功创建预约的 p` 只增；净报名 `N=Σ非取消 p` 等于 B；签到人数为另一个条件和。取消后重约会使 G 再增 p，但 B 回到原水平。G 不是独立人数，也不是到课人数。

## 3. 扣次不等于消费结算

当前 O02 在预约创建时已经减少可用次数，没有单独冻结余额；O07 只存在扣次与返次，签到不新增扣次。业务上可把它解释为“预约时预扣、符合取消规则时冲回”。它不证明财务收入或课消已经确认。

A03 模型定义未取消扣次为未冲回权益，不把它统称已消费：

`b + outstanding = b0`，其中 `outstanding = Σ每笔扣次绝对值 − Σ返次`。

若以后要区分冻结与课消，才引入 `available + reserved + consumed = funded`，并指定签到、上课完成或缺席事件何时把 reserved 转 consumed。当前需求没有足够事实裁定结算事件；本研究不增加结算功能。

## 4. 操作结果：成功、失败、未知

| 返回语义 | 精确定义 | 重试规则／可观察性 |
|---|---|---|
| SUCCESS（首次） | 创建／取消事务已提交；其全部资源变化符合后置条件 | 返回业务身份最清晰；当前 void 响应需用原 request_id 查询或重放确认 |
| SUCCESS（重放） | 已提交同会员、同键、同参数意图存在，返回原意图结果 | 即便原预约后来已取消，也不能重新创建；成功表示原创建曾成功，不表示现在仍预约中 |
| REJECTED | 已知准入不满足且本事务无副作用，或已明确回滚 | 同键“失败是否永久记忆”未确认；当前失败不留意图记录，后续资源改善可能成功 |
| ABORTED | SQL 死锁或异常后已确认整事务回滚 | 可在新事务有限重试；保留原 request_id，不从中间语句继续 |
| UNKNOWN | 客户端超时／连接断开，无证据判断是否已提交 | 保留同键向主库核验；不生成新键，不擅自返次或补占位 |

未知是观察者知识状态，不是预约持久态。服务进程返回前的提交失败可能由 Spring 代理抛出，Service 内“运行到最后一行”不足以称成功。

## 5. 决策优先级与状态迁移

以下创建表是在基础输入已合法且身份已确定后执行。`matched` 是同会员同键且 schedule/card/persons 全相同；`eligible` 是排课时间、上架、卡归属有效期课种门店等全部满足；`duplicate` 是同会员同排课存在 status∈{1,3}。创建时刻采用取得所需锁后的业务时钟，模型不枚举时间。

| 优先级 | 条件（首个匹配生效） | 结果／变化 | 来源 |
|---|---|---|---|
| C1 | 键已存在且参数不同 | 冲突，无副作用 | O02 |
| C2 | 键已存在且 matched | 原意图成功，无新增副作用；不因满额／过期拒绝 | O02；与资源已删除时锁前旧快照场景仍需补测 |
| C3 | 键不存在，eligible=false | 拒绝，无副作用 | O02/O06 |
| C4 | 键不存在，eligible=true，duplicate=true | 拒绝；新键不能规避同排课重复有效预约 | O04 |
| C5 | 上述通过，但 B+p>C 或次数卡 b<p | 拒绝，无副作用 | O02/O06 |
| C6 | 上述全部通过 | 新建 RESERVED；B+=p；次数卡 b-=p 并记 D=-p；年卡不记次数流水 | O02 |

逻辑优先级不强制所有资格检查的内部错误文案顺序；当前代码先校验容量再检查重复，可能在多个拒绝条件同时成立时返回“名额不足”。要求幂等重放成功优先于重新资格校验；其他多条件冲突的文案优先级属于 Q07。

会员取消表中 `owner` 必须先成立，不能因为别人已经取消就向越权请求返回成功。`deadline` 为 `now≤reservation.start−120分钟`，恰等于截止允许；时间精度与排队跨截止语义仍须确认。

| 优先级 | 当前条件 | 后置条件 | 来源 |
|---|---|---|---|
| U1 | 不存在或 owner=false | 拒绝／不泄漏他人记录 | O03 |
| U2 | CANCELLED | 成功重放，保留首次原因和时间，不再返次／释放 | O03 |
| U3 | CHECKED_IN | 拒绝 | O03 |
| U4 | RESERVED，但排课非已上架或 deadline=false | 拒绝 | O03；会导致排课已关闭的返次缺口 |
| U5 | RESERVED，全部满足 | CANCELLED/MEMBER；B-=p；存在原扣次则原额返原卡并插 R | O03；建议 B<p 时失败报警，替代钳制 |

系统取消建议表只在整体停课事件中生效；不受会员提前两小时限制；普通停课遇已签到先拒绝，不做部分取消。

| 优先级 | 条件 | 后置条件 | 来源 |
|---|---|---|---|
| S1 | 任一 CHECKED_IN，普通停课请求 | 整体拒绝，无变更；人工特殊处理另定义 | A04，来自 O13 的待实现意图，业务 Q03 |
| S2 | 排课 CLOSED 且所有待取消记录已处理 | 成功重放，不重复返次 | A01 |
| S3 | 排课 OPEN，合法停课／自动触发条件在锁内成立 | 同事务关闭排课；全部 RESERVED→CANCELLED/SCHEDULE；返原扣次并释放 B | A01；自动触发条件 Q01 |
| S4 | 排课 CLOSED，但遗留 RESERVED | 修复／恢复任务仍按原事件取消这些记录；不能看到 CLOSED 就退出 | A05；用于当前旧数据或分批处理恢复；不允许无原因地扫全库取消 |

S1 优先于 S2；S4 必须有可追溯排课关闭事件。本次小规模推荐 S3 一次事务，A05 不表示已经采用异步架构。

状态机的可达边：

```text
无预约 --Create--> RESERVED --MemberCancel--> CANCELLED(MEMBER)
                         \--ScheduleCancel--> CANCELLED(SCHEDULE)
                         \--CheckIn---------> CHECKED_IN
CANCELLED --重复任一取消--> CANCELLED（零副作用）
CHECKED_IN --普通取消-----> 拒绝
```

同一取消终态可以由不同原因到达，但资格、范围与排课前置转换不同，因此不能让系统任务直接调用会员取消 API。取消后重约是新实体，不是 CANCELLED→RESERVED。

## 6. 可验证不变量及破坏性反例

观察边界：仅检查已提交状态；同一事务内部允许暂时不等，其他业务读不得将半成品作为完成结果。审计跨表读取须同一一致快照。默认 A01、完整历史、禁止删除核心引用；当前实现不保证所有这些前提。

定义：`D(r)=原扣次绝对值（不存在为0）`，`R(r)=返次总额`；`L(c)=该卡全部次数流水 delta 之和`；`active={RESERVED,CHECKED_IN}`。以下检查编号对应 [audit.sql](实验/audit.sql)。

| 性质／为什么必须成立 | 精确定义、适用条件 | 破坏操作／最小反例 | 维护机制／独立检查 |
|---|---|---|---|
| I1 容量安全：已承诺人数可履约 | 每排课 `0≤B≤C` 且 `Σactive p≤C`；C>0、p>0 | 两个事务读 B=0、C=1，各写 B=1并插一人，计数未超但实际人数2；缩容到低于 B 也破坏 | 排课互斥、锁内缩容校验、增量条件；Q1 同时查计数及明细，不能只查 B≤C |
| I2 占位完整：冗余计数必须可重建 | `B=Σactive p`；绝对于 A01，不适用于 A02 封锁混记 | 自动取消不减 B；先释放后取消失败；`Math.max` 隐藏负值 | 统一同事务写入；Q1；故障断点前后比较四类表 |
| I3 卡不能透支：余额表示可用权益 | 次数卡 `b≠NULL ∧ b≥0` | 两次读1各扣1；允许负人数会把扣次变加次 | 参数域＋持卡锁＋`b>=p` 条件；Q2；非法域导入反例 |
| I4 返还不能创造权益 | 每预约 D≥0、`R∈{0,D}`；D=0时R=0；D/R各至多一笔，卡和会员相同 | 同时取消各返1；改了卡号返错卡；退款大于扣款；年卡误返 | 预约状态获胜者、唯一键、原扣次引用和同事务；Q3/Q4；去状态保护并去流水唯一性后重复取消 |
| I5 一次意图一次效果 | 每 `(member,key)` 唯一绑定 `(schedule,card,p)`；成功重放不改实体与账 | 超时重试换键；相同键换人数；旧快照下先校验满额再复查 | 请求唯一键＋参数比较＋锁后当前读；Q5只检索重复键，历史参数冲突须 API 差分测试 |
| I6 权益守恒 | `b=b0+L(c)`；完整历史且只有这些权益事件时成立；每流水 `after=before+delta` | 扣余额未记流水；记流水未扣余额；补偿返错金额 | 同事务、卡锁；Q2/Q6；独立期初与流水求和，不能仅用被测 Service 预期余额 |
| I7 实体与流水相容 | 次数卡每成功预约 D=p；取消后R=D，活跃R=0；年卡D=R=0 | 只变取消状态未返次；重复扣／缺扣；卡类型事后改变导致审计误判 | 原始卡类型不可变或保存扣次规则快照；Q3/Q4；现库无类型快照，类型不变是条件 |
| I8 唯一履约承诺 | 每 `(member,schedule)` active 记录数≤1，与人数是否多人无关 | 新键绕过重复检查，两个各占一人 | 同排课锁＋当前读；可选生成列唯一键；Q5 |
| I9 引用可追溯 | 预约所指排课、卡、会员存在；流水指预约和同卡同会员 | 管理删除已用卡导致无法返次；删除预约抹掉幂等历史 | 外键 RESTRICT 或统一引用校验并发锁协议；Q7；当前并未齐备 |

I1、I3、I4 的安全要求通常不随取消原因改变；I2、I6、I7 的具体公式依赖语义和账本完整性，不得脱离前提称“绝对”。若充值、人工调整存在，I6 必须把所有资金来源和去向计入，或使用可信期初余额，不能靠差额自动补流水掩盖问题。

单条流水 before/after 相等只证明单步算术，不证明余额全局正确；两条伪造流水各自相等仍可重复返次。若核对链式 before/after，必须按卡锁内分配的单调序号而不是 create_time 排序；本次先以期初＋总变动做终态守恒。

安全与活性分开：`永不重复返次` 是安全；`关闭的排课最终每笔应返预约都完成返次` 是活性。唯一键可以支持前者，但不会自动重跑中断任务。后者需持久事件、可恢复扫描、失败可观察和在数据库恢复等条件下的进展保证；本次未证明调度公平性。

## 7. 最小未决清单

| 问题 | 需要的原始业务例子／决策 | 依赖它的设计 |
|---|---|---|
| Q01 自动取消究竟为什么、何时触发 | 人数不足、行政停课、单笔撤销分别提供真实例子；两小时边界和本期是否启用 | 触发器和锁内判定；不能直接由旧状态图落地 |
| Q02 不释放的数字给谁看 | 要实时可售、累计报名、关闭快照还是封锁资源；会不会重开 | 是否分离封锁量；B 的定义和审计公式 |
| Q03 已签到时如何处理 | 普通停课拒绝是否满足运营；课程已发生能否退款 | 系统取消范围与补偿，而非一律返次 |
| Q04 停卡／过期卡的返还 | 返到账面但不可用是否可接受；卡删除是否绝对禁止 | 返次资格与权益可用性，不能误用预约资格拒返 |
| Q05 请求意图生命周期 | 失败重试是否允许转成功；键保存多久；原预约取消后旧键重试应显示什么 | 幂等存储、API 返回与保留策略 |
| Q06 时间依据与变更 | 快照和改期排课哪个决定截止；排队超过截止算谁的时间 | Clock 注入、时间边界与编辑约束 |
| Q07 多种拒绝同时成立 | 满额兼重复等优先返回哪种；排课关闭请求是否保证立即退款完成 | 错误契约与事务原子性范围 |

这些未决项不会阻止模型研究和实验，但阻止把系统取消方案当作已定需求投入生产。
