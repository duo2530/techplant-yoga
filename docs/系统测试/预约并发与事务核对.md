# 预约并发与事务核对

## 核对范围

围绕 `ReservationServiceImpl.create`、会员取消预约及相关排课、会员卡调用链，核对幂等、名额、扣次、事务回滚与状态并发。集成测试位于 `backend/ruoyi-yoga/src/test/java/com/techplant/yoga/reservation/service/ReservationServiceImplTest.java`，使用 Testcontainers MySQL 8.0、生产建表脚本及真实 Service、DAO，不连接开发库。

业务口径：同一会员允许预约时间重叠的不同排课；同一排课仍不允许重复有效预约；取消预约后允许重新预约。相同 requestId 只代表同一组排课、会员卡和人数。

## 规则、机制与测试证据

| 规则 | 当前实现机制 | 集成测试方法 |
|---|---|---|
| 相同请求只占位、扣次一次 | 首次幂等查询、取得锁后当前读复查、请求唯一索引 | `create_concurrentlySameRequestId_shouldBeIdempotent` |
| 等待期间首笔预约提交，即使已满也按重试成功处理 | 幂等复查早于排课资格校验，使用当前读 | `create_retryWithOldSnapshot_shouldReturnSuccessEvenWhenFull` |
| 相同请求标识不能换排课 | 参数一致性校验、同会员串行化 | `create_concurrentlySameRequestDifferentSchedule_shouldConflict` |
| 同排课不能重复有效预约 | 排课、会员锁及重复预约当前读 | `create_concurrentlyDuplicateSchedule_shouldAllowOnlyOne` |
| 不同排课允许时间重叠 | 不再进行跨排课时间冲突校验 | `create_concurrentlyOverlapping_shouldAllowBoth` |
| 最后一个名额只允许一人抢到 | 排课行锁、锁内检查和写入人数 | `create_concurrentlyLastSeat_shouldNotOversell` |
| 次数卡不能超扣 | 锁卡校验、余额条件扣减；同会员请求还受到会员锁串行化保护 | `create_concurrentlyInsufficientBalance_shouldNotOverdraw` |
| 创建中途失败不留下部分数据 | 预约、占位、扣次、流水共用事务 | `create_whenLedgerInsertFails_shouldRollbackEverything` |
| 取消中途失败不留下部分数据 | 状态、释放名额、返次、流水共用事务 | `cancel_whenLedgerInsertFails_shouldRollbackEverything` |
| 并发取消只返还一次 | 排课、预约行锁及状态复查 | `cancel_concurrently_shouldRefundOnlyOnce` |
| 停卡先提交，后来的预约不能成功 | 卡行锁及取得锁后的卡状态校验 | `create_whenStopCommitsFirst_shouldReject` |
| 预约先提交，再停卡不撤销既有预约 | 两个事务依卡锁顺序完成 | `stop_whenBookingCommitsFirst_shouldPreserveBooking` |
| 取消排课先提交，后来的预约不能成功 | 排课状态更新持有行锁，预约当前读检查状态 | `create_whenScheduleCancellationCommitsFirst_shouldReject` |

并发竞争测试以屏障同时放行两个请求；旧快照与状态先后测试通过外层事务和阶段信号，确保第二个事务在第一个事务提交前建立快照，不使用固定休眠。后者控制事务重叠和提交顺序，不断言每次调度都已进入数据库锁等待。

故障测试只在隔离数据库临时添加拒绝指定类型流水的 CHECK 约束，使预约或取消已经执行前序更新后发生真实 SQL 错误；测试结束删除约束。随后检查回滚并重试，不修改生产 SQL、不模拟业务依赖。

检查内容包括预约条数、各排课占位人数、余额、扣返次流水。公共断言校验有效预约人数与占位相等、余额非负、流水扣前扣后守恒，以及次数卡预约存在对应扣次流水；它仅用于本测试类中由完整业务流程生成的次数卡数据。

## 已发现的实现边界

1. **预约成功后再取消排课，尚无自动取消预约与返次。** `ScheduleServiceImpl.changeStatus` 当前仅更新排课状态；会员主动取消又要求排课仍为已上架，所以取消排课后会员无法通过当前取消接口取回次数。详细设计已将批量取消、返次及已签到处理列为待实现，不能把“取消先提交时预约会失败”的测试通过理解成完整闭环已完成。
2. **排课、会员与会员卡的删除引用限制尚未补齐。** 行锁只能安排当前事务先后，不能阻止后续删除已被预约引用的资源。
3. **没有据此认定全部锁顺序都不会死锁。** 校验预约时的范围锁、跨排课创建与取消交错、多会员独立预约等组合仍需覆盖；数据库死锁、连接中断、提交结果未知及客户端重试也不在本次故障注入范围内。
4. **本次保留会员锁及现有隔离级别。** 允许重叠预约后，会员锁是否移除应另行验证幂等、同排课重复预约和会员删除行为，避免同时变更业务规则与并发机制。
