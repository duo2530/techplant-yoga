# 预约并发与事务核对

## 核对范围

围绕 `ReservationServiceImpl.create`、加入排队、会员取消预约与补位及相关排课、会员卡调用链，核对幂等、名额、扣次、事务回滚与状态并发。集成测试位于 `backend/ruoyi-yoga/src/test/java/com/techplant/yoga/reservation/service/ReservationServiceImplTest.java`，使用 Testcontainers MySQL 8.0、生产建表脚本及真实 Service、DAO，不连接开发库。

业务口径：同一会员允许预约时间重叠的不同排课；同一排课仍不允许重复有效预约；取消预约后允许重新预约。相同 requestId 只代表同一组排课、会员卡和人数。

并发竞争测试以屏障同时放行两个请求；旧快照与状态先后测试通过外层事务和阶段信号，确保第二个事务在第一个事务提交前建立快照，不使用固定休眠。后者控制事务重叠和提交顺序，不断言每次调度都已进入数据库锁等待。例外是取消排队与补位竞争用例：补位方在外层测试事务中执行并暂停在提交前，主线程轮询 `information_schema.innodb_trx` 确认取消请求已进入锁等待，再放行补位方提交。补位方加入外层事务，沿用其可重复读；被验证的是取消方。

故障测试只在隔离数据库临时添加拒绝指定类型流水的 CHECK 约束，使预约或取消已经执行前序更新后发生真实 SQL 错误；测试结束删除约束。随后检查回滚并重试，不修改生产 SQL、不模拟业务依赖。

检查内容包括预约条数、各排课占位人数、余额、扣返次流水。公共断言校验已预约与已签到人数与占位相等、余额非负、流水扣前扣后守恒、占过名额的次数卡预约存在对应扣次流水，以及排队中与排队失败没有次数流水；它仅用于本测试类中由完整业务流程生成的次数卡数据。

多线程并发测试见[测试手册](AI%20Agent测试手册.md)的“预约并发正确性测试”，覆盖抢名额、同人连点、幂等重试、共卡抢次数、跨课跨人与混合预约排队取消六个场景，每轮结束后执行对账 SQL。

## 事务隔离级别

`ReservationServiceImpl` 的创建、加入排队、取消、人数不足自动取消与签到这五个写事务声明为读已提交（`Isolation.READ_COMMITTED`）。其它事务、数据源和 MySQL 实例仍使用默认的可重复读。Spring 只在开启新事务时应用该声明，方法加入调用方已有事务时沿用外层的隔离级别。

### 并发测试在可重复读下发现的问题

1. **不同会员之间的间隙锁死锁。** 幂等复查 `selectByMemberAndRequestIdForUpdate` 和重复预约复查 `selectOpenByMemberAndSchedule` 在记录不存在时会加间隙锁或 supremum 锁，与其他会员插入预约时在 `uk_member_request` 上的插入意向锁互相等待。`countQueuedForUpdate` 在可重复读下还保留扫描过但不满足条件的行锁。跨课跨人场景 1000 次预约中有 923 次死锁（MySQL 1213），混合场景有 24 次。
2. **取消排队时漏返次。** `cancel` 先用普通读查询预约以取得排课ID，可重复读的快照在这一步建立。之后它等待排课锁，其间他人取消预约触发补位，把这条排队记录转为已预约、扣次并提交。取消方取得锁后用当前读看到已预约，进入释放名额与返次分支，但查询扣次流水的普通读仍使用旧快照，查不到流水，因而不返次。混合场景 10 轮全部在“已取消且扣过次的预约已等额返次”对账上失败。

两个问题都只在可重复读下出现。读已提交下锁定读不加间隙锁，每条普通读都使用该语句开始时的快照，所以只改隔离级别，保留会员锁、全部 `FOR UPDATE` 复查、条件更新和唯一键，不增加重试或第二次流水查询。

### 读已提交下各决策依靠的记录锁

| 决策 | 保护机制 |
|---|---|
| 同会员 requestId 幂等、同排课不重复有效预约 | 先锁会员行，再当前读复查；所有预约插入都经过同一提交流程并持有会员锁，`uk_member_request` 兜底 |
| 名额不超卖 | 排课行锁和 `max_persons >= 新值` 条件更新；所有修改占位人数的路径都先持有排课锁 |
| 排队上限与补位顺序 | 排课行锁：排队记录只由加入排队在排课锁下插入，取消、补位、排队失败和自动取消对排队记录的状态转换也都在排课锁下执行 |
| 次数卡不透支、卡资格 | 卡行锁和余额条件扣减；停卡、启用卡锁同一卡行 |
| 预约状态转换 | 预约行锁和按原状态的条件更新 |
| 返次查扣次流水 | 扣次流水只由创建预约的事务或排课锁下的补位写入；取消在取得排课锁后普通读，能看到已提交的扣次；状态转换获胜者与 `uk_reservation_type` 保证只返一次 |
| 排课状态 | 排课状态更新持有排课行锁，预约取得锁后读到已提交的状态 |

逐项核对后，没有决策依赖间隙锁防幻读，`MemberCardService.stop` 和 `ScheduleService.changeStatus` 不需要改动。生产库若开启 binlog，读已提交要求 `binlog_format` 为 ROW 或 MIXED（MySQL 8 默认 ROW）；仓库没有生产实例的 binlog 配置，部署前需确认。

## 已发现的实现边界

1. **管理员手动取消排课后，尚无批量取消预约与返次。** 人数不足自动取消已批量取消并返次；`ScheduleServiceImpl.changeStatus` 的手动取消仍仅更新排课状态；会员主动取消又要求排课仍为已上架，所以取消排课后会员无法通过当前取消接口取回次数。详细设计已将批量取消、返次及已签到处理列为待实现，不能把“取消先提交时预约会失败”的测试通过理解成完整闭环已完成。
2. **排课、会员与会员卡的删除引用限制尚未补齐。** 行锁只能安排当前事务先后，不能阻止后续删除已被预约引用的资源。
3. **没有据此认定全部锁顺序都不会死锁。** 并发测试在读已提交下 60 轮未出现死锁，但随机并发测试不能证明锁图无环；跨排课补位与停卡交错、会员删除等组合仍未覆盖。连接中断、提交结果未知及客户端重试也不在本次故障注入范围内。
4. **手动取消排课后排队记录不落库为排队失败。** 展示与筛选按排课状态推导为排队失败；人数不足自动取消把排队中记录落库为已取消（排课取消）。
5. **补位锁序。** 补位在持有排课锁的前提下锁排队记录再锁其会员卡；不同会员的卡锁与预约创建路径的卡锁不形成环，但未对跨排课补位与停卡交错做专门的死锁测试。
6. **保留会员锁。** 预约写事务改为读已提交后，会员锁仍是同会员幂等与重复预约判断的串行化依据。是否移除应另行验证幂等、同排课重复预约和会员删除行为，避免同时变更业务规则与并发机制。
