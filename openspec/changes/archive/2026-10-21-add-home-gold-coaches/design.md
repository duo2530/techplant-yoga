# Design

## Context

动机见 proposal.md。已核对的实现与约束如下：

- 首页 `frontend/uni-app/pages/home/index.vue` 使用真实门店接口，独立维护换店弹层，没有教练区块。
- `api/coach.js` 的 `getFeaturedCoaches()` 和 `listCoaches()` 为固定空结果；`pages/coaches/index.vue` 虽登记为“约教练”，实际展示全部教练列表，没有调用方依赖其列表入口。
- `CoachDO` 只有姓名、头像、简介、电话、相册与审计字段。DAO 资料更新显式指定列；管理端列表不读取简介、相册。
- `SchedulePublicController` 的 `GET /api/schedules` 强制门店、课种、单日日期；`ScheduleServiceImpl.publicPage` 负责卡片装配。公开可见性为排除待上架，包含已取消与已结束状态；日期窗口为今天起 14 天。
- 教练属于平台主数据，不归属门店；相册最多 5 张。`UC-001`、`UC-007` 和用例总览仍禁止首页金牌区，教练管理详细设计却残留等级接口设计，存在文档冲突。本次采用用户确认的新需求，实施时统一文档。
- 视觉参照为 `docs/产品分析/用户端小程序截图/P1-首页-06-约教练.png`，其中课程卡只有时间；跨日列表需补日期，系统导航栏及微信胶囊由平台绘制。

## Goals / Non-Goals

**Goals:** 用单独的金牌设置操作和公开只读模型串起后台、首页及教练页；复用排课卡装配、公开可见性和预约约束；保持现有单日约课接口兼容。

**Non-Goals:** 不增加教练与门店关系、头衔、技能、推荐权重、用户端全部教练入口；不把原型中的样例人物、星级或剩余人数写成固定数据。

## Decisions

### 1. 持久化等级并独立更新

`t_coach` 新增 `level tinyint NOT NULL DEFAULT 1`，限定 1 普通、2 金牌。管理端列表及详情增加 `level`，列表增加标识及“设为金牌／取消金牌”操作。采用 `PUT /admin/coaches/{coachId}/level?level=1|2`，成功返回 `{code,msg}`；不存在返回 404，非法值返回 400，重复设置成功。写操作记录当前管理员及更新时间。

资料创建固定普通等级，资料更新不接管 `level`，DAO 保留独立更新列，避免旧客户端资料编辑覆盖等级。等级接口与教练新增、修改、删除一致，只要求管理端登录，前端按钮不配置额外权限。新建库不创建独立等级按钮；已有库增量脚本清理已废止的等级按钮及角色绑定，不影响其它菜单授权。HTTP 集成测试验证普通管理员可操作、游客及用户端会员不可写。

等级端点由 `CoachController.updateLevel` 承载，与教练资料接口放在同一个 Controller；该 Controller 继承 `BaseController`，参数绑定与校验错误由 `GlobalExceptionHandler` 统一返回业务码 400。管理端请求函数统一维护在 `frontend/pc/src/api/coach/coach.js`，页面通过 `updateCoachLevel(coachId, level)` 调用等级端点。

选择等级字段是为了衔接仓库已有等级设计；不恢复其中头衔、状态等与本需求无关的旧字段。资料表单内增加可选开关会让全量编辑与等级修改耦合，因此不采用。

### 2. 公开接口使用专用模型

| 接口 | 请求 | 成功数据 |
|---|---|---|
| `GET /api/coaches/featured` | 无参数 | `{code,msg,data:[{id,name,avatarUrl,intro}]}`，全部金牌，`id DESC` |
| `GET /api/coaches/{coachId}` | 路径 ID | `{code,msg,data:{id,name,avatarUrl,intro,gallery:[]}}` |
| `GET /api/coaches/{coachId}/schedules` | 必填 `storeId`、`courseType`；分页默认 `pageNum=1,pageSize=10`，上限 100 | `{code,msg,rows:[ScheduleCardVO],total}` |

列表一次读出所有金牌，不复用管理端分页接口，避免受前 100 条截断及敏感字段暴露影响。详情不要求仍为金牌，取消标记不使现存教练链接失效。不存在的教练、门店返回 404，非法 ID、课种或分页返回 400。大整数 ID 沿用项目字符串序列化约定。

公开 controller 按既有 `@Anonymous` 方式声明。`MemberSecurityConfig` 对 `/api/**` 使用独立过滤链，当前白名单只有门店和排课，必须将上述三个教练只读路径按 GET 显式加入会员安全链白名单，仅添加注解不足以放行。VO 不包含 `phone`、审计字段或管理数据对象。前端 API 复用 `utils/request`，设置公开请求标志，归一化字符串 ID 与图片 URL。历史相册只读取项目真实字段 `gallery`，不沿用旧原型的 `albumUrls`。

### 3. 为教练页增加专用排课查询

截图没有日期选择器，采用“当前门店＋所选教练＋课种＋今天至第 13 天”的查询窗口，页面标明“当前门店 · 未来14天”，日期来自服务端业务时区（Asia/Shanghai）。跨日卡片增加日期，不加入截图之外的日期选择条。

在 schedule 模块增加教练场景的 query/service/DAO 路径，固定范围由服务端计算，条件在数据库分页前完成。复用公开可见条件、按 `course_type` 快照筛选、卡片装配及 `bookable` 推导，按 `start_time ASC,id ASC` 排序。现有单日 `GET /api/schedules` 的参数与行为保持原状。

不在前端拉取 14 天全部门店排课后筛选教练：该方式增加请求量，而且分页总数及空态可能错误。新增查询如需抽取卡片装配公共方法，应维持原接口响应一致。教练页默认团课，其他三类遵循项目 1～4 枚举；已取消、已结束和满员场次按现有状态展示，预约仍由现有链路校验。

### 4. 首页与教练页独立加载

首页在门店卡后渲染全部教练卡，白底及字号、间距复用 `$ys-*` 设计 token。`onShow` 单独刷新金牌列表，不串行等待门店请求；门店为空也展示金牌列表。新增加载／空／错误状态，失败可重试；刷新或重试期间避免重复提交及旧结果覆盖。中性头像占位不使用现存某位教练照片。

复用 `pages/coaches/index.vue` 路由，改为 `/pages/coaches/index?coachId=<字符串ID>` 的单教练页面，不新增同义路由。详情查询与排课状态独立，无有效门店仅显示资料并提示回首页选店。课种切换清空旧分页，使用请求序号校验响应归属；重试不跳页。默认每页 10 条，显示加载更多／末尾状态，并提供显式加载更多按钮，保障 H5 和小程序都可操作；小程序触底可复用同一加载方法。

资料区按截图建立渐变背景、白色圆角面板、头像及相册，图片可预览；课程卡沿用已核对的 `/pages/detail/index?scheduleId=<排课ID>`，不创建第二套预约逻辑。页面返回重新显示时校准当前门店，门店改变则重置排课；课种保留当前选择。

### 5. 界面验收以 H5 为准

按 `docs/系统测试/AI Agent测试手册.md` 使用真实 MySQL 的 Testcontainers 集成测试和连接隔离后端的 Playwright。先复用既有 coach、schedule 数据夹具及公开 HTTP 测试装配，再补等级默认值、独立更新、权限、101 位全量列表、字段隐私、删除、窗口边界、课种快照、状态可见性及分页排序。测试时钟需固定在业务时区，避免跨日边界不稳定。

H5 端到端覆盖后台标记到首页出现、卡片进入正确详情、图片和相册、切换 Tab、加载更多及课程详情，网络故障与乱序响应可拦截。管理端当前未接入 Playwright，补最小独立测试入口和标记流程，不扩展为整个管理端测试工程。

本次界面验收仅要求 H5，使用已安装的 agent-browser 在移动视口中访问实际 H5 页面，核对截图布局、页面导航、相册预览、课种切换、显式加载更多与返回状态，保存关键截图和操作结果。agent-browser 用于浏览器交互验收，Playwright 保留可重复执行的回归用例。H5 中不以触底生命周期作为分页验收前提，使用显式加载更多按钮完成验证；不安排微信开发者工具或真机验收。小程序仍保留兼容实现及构建检查，H5 结果只报告为 H5 验证通过。构建及静态检查作为辅助检查，不替代行为验证。

## Risks / Trade-offs

- [首页全量响应和渲染随金牌数量增长] → 本次按用户明确要求全量返回，仅传列表必要字段、头像延迟加载；不能暗中加截断，后续变更分页需另行确认需求。
- [参考截图与跨日真实数据存在差异] → 补充日期和窗口说明，以截图约束视觉层级，课程字段以真实接口为准。
- [既有教练页被重新定义] → 检查页面注册、静态自检和所有调用方；无参数直达显示参数错误，不退回全部教练列表。
- [等级操作与资料编辑并发] → 更新列互不覆盖，测试编辑后等级保持不变，避免读取旧实体后全字段回写。
- [旧文档与新功能冲突] → 同步 UC-001、UC-007、用例总览、业务规则和接口设计，不将旧“无金牌”条款继续作为验收依据。

## Migration Plan

1. 同时提供新建库 `yoga.sql` 更新和面向已有库的独立增量 SQL，只增加等级列并将既有数据默认设为普通，不执行重建表或样例金牌回填。
2. 先在隔离库验证已有数据升级、新建库及原教练增删改查兼容，再发布后端、管理端和用户端。后端上线前不得先发布调用新接口的用户端。
3. 由管理员选定真实金牌教练；刚升级无人标记时首页显示空态属于预期。
4. 回滚先退用户端及管理端再退后端，保留新增列与等级数据；旧代码显式资料更新列可继续运行。需要撤销数据库列时另行备份和执行维护操作，不自动丢弃金牌配置。
