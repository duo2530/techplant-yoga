## 瓶颈证据

### 1. 拐点由后端 2 vCPU 和 Druid 的 20 个连接共同决定

- 每个请求平均持有连接的时间，按 Druid 活跃连接平均值除以 QPS 计算。这个时间随负载增长：
  - 100 QPS 时 13.8 ms。
  - 220 QPS 时 17.9 ms。
  - 300 QPS 时 27.7 ms。
  - 380 QPS 时 40.8 ms。
  - 420 QPS 时 44.7 ms。
- 用 20 个连接除以持有时间，得到连接池能撑的上限。420 QPS 时这个上限约为 447 QPS，所以 460 超过了连接池容量。
- 同一时段后端 JVM CPU 平均 0.838，云监控显示 79~87%。MySQL CPU 为 63~70%，压测机低于 5%。持有时间变长，主要来自后端 CPU 接近饱和。
- 到达率一旦超过上限，排队就会不断变长：
  - Druid 等待线程最多到 779。
  - Tomcat 忙线程顶到 800 的上限。
  - k6 丢弃了 3571 个迭代。
  - 21% 的请求超过 10 秒客户端超时。
- 行锁等待（460 时 2721 次，平均 21.94 ms）只在崩溃后出现，是结果而不是起因。420 及以下各级的行锁等待都是 0。

### 2. 同人同课有效预约查询随会员历史预约数线性变慢

这条查询是 `selectOpenByMemberAndSchedule`（`... WHERE member_id = ? AND schedule_id = ? AND status IN (1,3,4) LIMIT 1 FOR UPDATE`）。它在各轮的表现如下：

| 运行 | 表内预约 | 调用次数 | 平均 ms | 最大 ms | 每次扫描行数 |
|---|---|---|---|---|---|
| S/empty-300（空表起跑） | 0 → 36001 | 36001 | 0.373 | 41.738 | 6.7 |
| S2/loaded-300 | 192001 → 228002 | 36000 | 1.042 | 61.293 | 83.5 |
| S2/loaded-460 | 228002 → 277201 | 49199 | 1.961 | 33.011 | 100.5 |

- EXPLAIN 显示，这条查询用的是 `uk_member_request(member_id, request_id)` 的 `member_id` 前缀，`rows 98`，`filtered 0.08`。也就是说，它要扫完该会员名下的全部预约，再按排课和状态过滤。
- 表里没有 `(member_id, schedule_id)` 索引。
- 每次扫描的行数约等于「预约总数 / 2500 个会员」：228002 / 2500 = 91，接近实测的 83.5 到 100.5。所以耗时随会员的历史预约数线性增长。
- 每次预约的 SQL 总耗时在 300 QPS 下从 2.52 ms 增加到 3.34 ms。其余写路径语句在这两轮的平均耗时都在 0.14 到 0.34 ms，每次扫描最多 1 行。
- 这部分只占连接持有时间（300 QPS 时 22.5 到 27.7 ms）中的一小部分。连接持有时间的大头在后端 CPU 上。
- 这条查询解释了空表和大数据量下 460 QPS 结果不同的方向，但还不能单独说明崩溃的全部原因。加索引后，需要在同样的 22.8 万条数据上复测 460 QPS 验证。

### 3. B-burst：同一排课的行锁串行化，加上连接池排队

B-burst 中，500 个请求同时争同一行排课：
- 行锁等待 496 次，平均 68.87 ms。
- Druid 活跃连接顶到 20，等待线程最多 129。
- `NotEmptyWaitCount` 增加 827 次，累计 `NotEmptyWaitMillis` 365156 ms。
- 后端和 MySQL 的 CPU 都很低（每分钟平均 4.3% 和 0.9%）。

所以 B-burst 的延迟来自锁和连接排队，与算力无关。每个请求都要拿同一行的 `FOR UPDATE`，事务只能逐个执行。20 个连接都被等锁的事务占住时，后来的请求还要再排连接。B 的匀速版本（每秒 50 个）只有 4 次行锁等待，p99 20.67 ms。

### 4. 偶发 1 到 2 秒停顿，原因未查明

以下运行出现了 p99 或 max 突刺。保留了采样的轮次中，同一时段 Druid 等待线程和 Tomcat 忙线程都短时间升高：

| 运行 | 情况 |
|---|---|
| C/rate-0240 | p99 2389.92 ms，max 4048.11 ms，丢弃 86，Tomcat 忙线程 528 |
| R/r220-3 | p99 535.37 ms，max 1293.86 ms |
| C2/rate-0300 | p99 811.84 ms，max 1660.24 ms |
| S/empty-300 | p99 661.05 ms，max 1618.37 ms |
| D/preload | p99 822.84 ms |

- 同参数的 S2/preload 没有出现突刺（p99 104.87 ms）。
- 停顿期间 MySQL 没有告警，也没有死锁。
- 停顿期间压测机 CPU 低于 9%，所以停顿出在服务端。
- GC 停顿是猜测，因为这次没有开 GC 日志，无法证实。
- 场景 A 的 10 分钟里没有出现停顿（max 97.38 ms）。但 A 的 p99 目标是 800 ms，一次停顿就可能让 2 分钟窗口内的 p99 超标。所以这一项需要单独跟踪。

## 数字核对（benchmark-checklist）

1. **为什么不能翻倍。** 瓶颈是后端 CPU 和连接池，见「瓶颈证据」第 1 条。压测机 CPU 最高 8.5%，没有测成压测机的上限。
2. **是否按生产配置运行。** 后端的 JVM、Druid 和 Tomcat 都用仓库默认配置，MySQL 开启双 1 持久化和 ROW binlog。压测环境与生产的差异只有 SAE 规格（后端 2C4G）和 Jolokia 只读采集。拐点数字只适用于这个规格，换规格要重测。
3. **是否超出物理极限。** 420 QPS × 每请求约 4 ms CPU（按 2 核 × 84% / 420 计算）在 2 核的容量内。每秒提交数与 QPS 一致，fsync 次数也在正常范围，没有超出物理极限的数字。
4. **是否有错误。** k6 按 5xx、连接失败、10 秒超时和 code 500 计错误，409 按 msg 分类，未分类 409 和非预期响应都是 0。正确性靠对账确认，每轮违规都是 0。
5. **能否复现。** 各项的运行次数如下：
   - A：1 轮 10 分钟。issue 要求跑一轮。
   - 220 / 240：交替各 3 次。
   - 空表 420 / 460：交替各 2 次。
   - 大数据量 460：3 次，全部崩溃。
   - 这些都没有达到清单要求的每组 5 次。拐点的判断依据是「通过与崩溃」这种大差异，不是小幅变化。但 440 QPS 没有测过，所以拐点的精度是 40 QPS。
6. **对用户是否有意义。** 测的就是用户实际等待的完整 HTTP 接口，数据量覆盖空表到 27.7 万条预约。
7. **请求是否真的执行。** 除了超时后仍提交的请求，每轮的成功数都等于 `Com_commit`，`Innodb_rows_inserted` 约为成功数的 2 倍，因为每次成功都写入一条预约和一条流水（A 为 120010 对 60000）。对账汇总和成功数一致，请求都落库了。

## 问题与证据缺口

- **OFFSET 缺陷。** 中途重建压测机镜像时，`reservation.js` 里的 OFFSET 被误删了，导致 S/loaded-300 的 36001 个请求全部返回 409「您已预约该课程」。这一轮已经剔除，不在本目录中。
  - S/empty-300 是从空表起跑的，不依赖 OFFSET，结果有效。
  - A、B、C、C2、R、R2、D 用的是更早的镜像，那个镜像里有 OFFSET，也都有效。
  - 缺陷已修复，并在镜像内核对过代码。
- **R、R2、D 的原始文件丢失。** 这三组的 k6 summary 在重新部署压测机时丢了，上面表格里的数字摘自当时的控制台输出。其余运行的原始文件都在本目录。
- **CPU 口径。** k6 summary 里没有 CPU。CPU 数字一部分是 JVM `ProcessCpuLoad` 每 2 秒的采样平均，另一部分是云监控的每分钟平均，两者不完全一致：420 QPS 时 JVM 为 0.838，云监控为 79~87%。
